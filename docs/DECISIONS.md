# 의사결정 기록 (DECISIONS)

백엔드 연동 과정에서 확인 없이 스스로 판단한 사항과 근거를 정리한다.

## 아키텍처

### 26. 레이아웃 정리 + "차단(blocking)" 개념 제거 (Phase H)

공간이 남아돌고 카드가 좁다는 피드백에 맞춰 UI 밀도를 낮췄다.

- 좌측 내비를 `w-44 → w-56` 로 넓혔다.
- 보드 칸반 컬럼은 폭을 고정(`w-72 shrink-0`)했다. 화면이 좁아져도 컬럼/버튼 글자가 줄바꿈되거나 찌그러지지 않도록 헤더 버튼에도 `shrink-0 whitespace-nowrap` 을 줬고, 대신 보드 영역 전체가 가로 스크롤되게 했다. 카드의 `compact` 축소 표기는 없애 항상 큰 제목으로 보이게 했다.
- 오른쪽 "메모/이슈 로그" 패널을 열고 닫는 오버레이에서 **항상 보이는 우측 도킹 패널**(`ProjectNotesPanel` 을 `<aside>` 로 리팩토링)로 바꿨다. 보드 상단의 "메모" 토글 버튼과 관련 상태를 제거했다.
- **차단(blocking) 개념을 전면 제거**했다. 사용자가 의미를 이해하기 어렵고 실사용에서 불필요했다. `tasks.is_blocking`/`template_items.is_blocking` 컬럼(0009), 타입/매퍼/검증, 보드의 "차단 항목만" 필터·"미완료 차단 N건" 통계, 카드/상세의 차단 배지, 생성/템플릿 편집 폼의 차단 체크박스를 모두 없앴다.

### 27. 보관함은 좌측 내비의 별도 페이지, 메모 패널과 분리 (Phase H 후속)

처음에는 우측 메모 패널을 탭(메모/보관)으로 확장하려 했으나, 두 기능은 스코프가 다르다는 지적에 따라 되돌렸다. 메모는 **지금 보고 있는 프로젝트 하나**에 귀속되는 정보이고, 보관함은 **여러 프로젝트를 가로지르는 탐색/목록** 기능이라 같은 패널에 둘 이유가 없다.

- 우측 패널은 원래대로 메모 전용(`ProjectNotesPanel`)으로 유지한다.
- 보관함은 좌측 내비에 새 메뉴(`/archive`)로 추가했다. `ArchiveView` 가 `status = 'archived'` 인 프로젝트만 모아 이름·설명·보관일·항목 수(`getProjectTaskCounts`)를 보여주고, 클릭하면 해당 대시보드(`/?project=<id>`)로 이동하며 "재개" 버튼으로 다시 활성화(`setProjectArchived`)할 수 있다.
- 대시보드 생성 시 선택 입력으로 `projects.description`(0010 마이그레이션)을 추가해, 보관함 목록에서 그 대시보드가 어떤 목적이었는지 알 수 있게 했다.

### 28. 보관함 "재개" 대신 "삭제"
보관된 회차를 다시 활성화하는 "재개" 기능은 실사용 시나리오에 없어 제거하고, 대신 완전 삭제(`deleteProject`)로 바꿨다. 오작동 방지를 위해 `status = 'archived'` 인 회차만 삭제를 허용한다(활성 회차는 API 단에서 거부). `tasks.project_id` FK 는 원래 `ON DELETE` 동작이 없어(NO ACTION) 프로젝트 삭제 시 FK 위반이 났는데, 0011 마이그레이션에서 `ON DELETE CASCADE` 로 바꿔 프로젝트 삭제 시 소속 tasks 가 함께 지워지고, tasks 에 이미 걸린 CASCADE(comments, task_history)/SET NULL(notification_log)이 연쇄적으로 정리되게 했다. `project_notes` 는 애초에 CASCADE 였으므로 그대로 함께 삭제된다.

### 29. 보관된 회차 read-only 완전 강화 (Phase I)

보관된 회차에서 상태 변경/담당자 변경/항목 생성은 이미 서버(`projectWriteError`)에서 막고 있었지만, **코멘트 작성(`addComment`)·수동 알림(`notifyTaskNow`)·항목 수정(`updateTask`)은 서버 가드가 빠져 있어 실제로 동작하는 버그**였다. 세 액션 모두 `projectWriteError` 체크를 추가했다. 클라이언트도 `TaskDetailView` 가 `readOnly` 를 몰라 상세 페이지에서는 위 버튼들이 항상 보였는데, `/tasks/[id]` 페이지에서 `getProjectById` 로 소속 프로젝트 상태를 조회해 `readOnly` 를 내려주고 상태변경/코멘트입력/알림/수정 UI 를 숨기도록 고쳤다(보드 카드는 이미 정상 동작하고 있었음).

### 30. 브라우저 첫 방문 시 실제 팀원으로 오인 귀속 방지 (Phase I) — 결정 33 에서 대체

`CurrentUserProvider` 가 로컬 저장값이 없을 때 멤버 목록의 **첫 번째(가나다순)** 멤버를 자동 선택하고 있었다. 실사용 중인 멤버가 여럿이면 "아직 아무도 선택 안 한 새 브라우저"가 실제 팀원(예: 알파벳/가나다순으로 앞선 사람) 이름으로 조용히 기록되는 문제로 이어진다. `DEFAULT_MEMBER_ID`(고정 uuid) 를 도입하고, 0012 마이그레이션으로 이 id 의 멤버(`홍길동`, 명백한 플레이스홀더 이름)가 항상 존재하도록 보장한 뒤, 저장값이 없을 때는 이 플레이스홀더를 우선 선택하고 그마저 없으면(멤버가 아예 없는 새 회차 등) `null` 로 두어 명시적 선택을 요구하도록 바꿨다.

### 31. 멤버(담당자)는 회차(프로젝트)에 귀속 — 전역 공유 제거 (Phase I)

- **문제**: `users` 가 전역 테이블이라 모든 회차가 같은 멤버 목록을 공유했다. 회차(예판)마다 참여 팀 구성이 달라질 수 있는데, 지난 회차 멤버가 새 회차에도 계속 보이고 "현재 사용자" 후보에도 무관한 사람이 섞이는 문제가 있었다.
- **결정**: 멤버는 회차 하나에만 속한다(다대다 공유 안 함, 회차마다 완전히 별개의 목록). 같은 사람이 여러 회차에 참여해도 회차마다 새로 등록해야 한다. 대신 구현이 단순해지고("이 멤버가 어느 회차 것인지" 혼동이 없음), 새 회차는 항상 멤버 0명으로 시작해 실수로 무관한 사람이 섞이지 않는다.
- **스키마(0013)**: `users.project_id`(not null, `projects` FK, `on delete cascade`) 추가. 기존 멤버는 "가장 최근 활성 회차"(없으면 최신 회차)로 일괄 이관했다. 이메일 유일성 범위를 전역(`users_email_key`) → `(project_id, email)` 로 완화해 같은 사람이 여러 회차에 각각 등록될 수 있게 했다. 프로젝트 삭제(0011의 CASCADE) 시 그 회차 멤버도 함께 삭제되는데, `notification_log.user_id` 가 CASCADE 가 아니어서 알림 발송 이력이 있으면 삭제가 막히는 문제가 있어 이것도 CASCADE 로 바꿨다.
- **템플릿과의 충돌 해소**: 템플릿(`template_items.default_assignee_id`)은 여러 회차에 재사용되는데 멤버는 이제 회차별로 다르므로, 특정 회차 멤버 id 로 "기본 담당자"를 고정하면 다른 회차에 적용할 때 그 멤버가 없어 깨진다. `default_assignee_id` 를 없애고 자유 텍스트 힌트 `default_assignee_name` 으로 낮췄다. 템플릿 적용(`createTasksFromTemplate`) 시점에 `TemplateUseModal` 에서 항목별로 지금 회차의 실제 멤버 중 담당자를 고르며(힌트와 이름이 같은 멤버가 있으면 미리 선택해줌), 서버는 선택된 담당자가 실제로 그 회차 멤버인지 검증한다.
- **UI 위치**: "현재 사용자" 선택과 "멤버 관리"는 전역 좌측 내비가 아니라 보드/템플릿/항목 상세 등 **회차 맥락이 있는 화면**의 헤더로 옮겼다(`CurrentUserPicker`). `CurrentUserProvider` 도 레이아웃 전역이 아니라 각 페이지에서 그 회차의 멤버로 초기화한다. `localStorage` 키도 회차별로 네임스페이스(`bo-current-user-id:{projectId}`)해, 같은 사람이라도 회차마다 다른 id 로 선택 상태를 유지한다.
  - → "현재 사용자" 부분은 결정 33 에서 대체됐다(회차와 분리된 브라우저 설정 + 본인 직접 입력). 멤버 목록이 회차에 귀속된다는 결정 자체는 그대로 유효하다.

### 32. 새 대시보드 생성 시 기존 활성 회차 보관을 선택 아닌 필수로 (Phase I)

"새 대시보드" 생성 모달에 "현재 대시보드를 보관"이라는 체크박스가 있어, 체크를 해제하면 활성(`status = 'active'`) 회차가 두 개 이상 동시에 존재할 수 있었다(실제로 발생함). 활성 회차가 여럿이면 `resolveCurrentProject()` 가 그중 하나만 "현재"로 골라 다른 활성 회차가 사실상 접근하기 어려운 상태로 방치된다 — 있어서는 안 되는 상태다.

- 체크박스를 없애고, `startNewDashboard` 가 새 회차를 만들기 전에 **`status = 'active'` 인 회차를 예외 없이 전부 보관 처리**하도록 바꿨다(특정 id 를 받아 보관하던 방식 → 조건절로 일괄 보관). 이제 "활성 회차는 항상 최대 1개"라는 불변식이 클라이언트가 뭘 넘기든 서버에서 항상 지켜진다.
- 이미 활성 회차가 2개 이상 쌓여 있던 기존 데이터를 되돌리기 위해 0014 마이그레이션에서 가장 최근에 만든 활성 회차만 남기고 나머지를 보관 처리했다.

### 33. "현재 사용자"는 회차와 분리된 브라우저 설정 + 본인이 직접 입력 (Phase J)

회차별 멤버로 바꾼 뒤 "현재 사용자" 선택도 회차별 드롭다운(헤더)에 뒀는데, 두 가지가 문제였다. (1) 헤더 구석의 작은 select 라 지금 누구로 기록되는지 눈에 잘 안 들어온다. (2) 회차를 옮기면 선택이 초기화된다 — "내가 누구인지"는 회차와 무관하게 유지돼야 하는 정보다.

- **저장 단위 분리**: 브라우저에는 회차와 무관한 본인 정보(`{ name, email }`)를 단일 키(`bo-current-identity`)로 저장한다(`CurrentIdentityProvider`, 전역 레이아웃). 회차별 멤버 행과의 연결은 `ProjectMemberProvider` 가 **이메일**로 매칭해 처리한다. 멤버 행 id 는 회차마다 다르지만 같은 사람의 이메일은 회차를 가로질러 같기 때문이다. 회차별 `localStorage` 네임스페이스(결정 31)는 폐기했다.
- **선택이 아니라 입력**: 멤버 전체 목록을 드롭다운으로 주면 남의 이름을 클릭 한 번으로 고를 수 있어 잘못된 귀속이 너무 쉽다. 좌측 내비 하단에서 본인 이름·이메일을 직접 입력받고(`IdentityModal`), 입력 전에는 `currentUser` 가 `null` 이라 기록이 남는 모든 동작이 막힌다. 이 때문에 플레이스홀더 기본 멤버(결정 30, `홍길동`)는 목적을 잃어 앱 코드에서 참조하지 않는다(마이그레이션 0012 파일은 이력 유지를 위해 남겨둠).
- **미소속은 조용히 실패시키지 않는다**: 입력한 이메일이 지금 회차의 멤버가 아니면 아무 작업도 할 수 없으므로, 화면 상단에 알림(`MembershipAlert`)을 띄우고 그 자리에서 "이 대시보드 멤버로 추가"할 수 있게 했다. 보관된 회차는 어차피 쓰기가 막혀 있어 띄우지 않는다.
- **UI 위치**: 좌측 내비 하단에는 현재 사용자(아바타·이름·이메일)만 상주하고, 회차에 귀속된 멤버 목록 관리는 각 프로젝트 화면 헤더의 "멤버" 버튼(`ProjectMembersButton`)에 남긴다.

### 34. 보드의 "템플릿" 버튼은 이동이 아니라 선택 팝업 (Phase J)

보드에서 템플릿을 쓰려면 `/templates` 로 이동한 뒤 다시 보드로 돌아와야 해서, 보드 맥락이 끊겼다. 버튼을 누르면 저장된 템플릿을 고르는 팝업(`TemplatePickerModal`)이 뜨고, 고르면 기존 항목별 담당자 지정 단계(`TemplateUseModal`)로 이어져 지금 회차에 바로 항목이 생성된다. 항목이 0개인 템플릿은 생성 자체가 불가능하므로 선택을 막았고, 템플릿 편집이 필요하면 팝업 하단 링크로 관리 화면에 갈 수 있다. 보드와 템플릿 화면이 같은 데이터를 쓰므로 조회는 `getTemplatesWithItems()` 하나로 합쳤다(템플릿마다 쿼리를 날리지 않고 항목을 한 번에 읽어 묶는다).

### 35. 항목 상세의 "목록으로"는 그 항목이 속한 회차로 돌아간다 (Phase J)

`router.push('/')` 로 고정돼 있어, 보관된 회차의 항목을 열었다가 나오면 활성 회차 보드로 튕기는 버그가 있었다. 항목은 자기 회차를 알고 있으므로(`task.projectId`) `/?project=<projectId>` 로 돌아가게 고쳤다.

### 36. 세팅 환경은 STG / PROD 두 개 (Phase J)

실제로 쓰는 환경은 STG 와 PROD 뿐이고 DEV 는 존재하지 않는다. postgres enum 은 값 삭제가 불가능하므로 0015 마이그레이션에서 새 타입(`('stg', 'prod')`)을 만들어 `tasks.environment`·`template_items.environment` 를 갈아끼웠다. 기존 `dev` 항목은 지우지 않고 `stg` 로 옮겼고, 부르는 이름과 코드가 어긋나지 않도록 `prd` 값도 `prod` 로 함께 바꿨다(해당 컬럼에는 default·인덱스가 없어 타입 교체만으로 충분했다). 환경 선택 UI 4곳에 하드코딩돼 있던 option 목록은 `ENVIRONMENTS` 배열로 모아, 환경이 바뀔 때 고칠 곳이 상수와 마이그레이션 두 군데로 줄었다.

### 37. 템플릿은 대시보드에 귀속되지 않는 공용 자산 (Phase J)

`/templates` 화면이 활성 회차를 조회해 "생성 대상" 표시·멤버 관리 버튼·미소속 알림·"이 템플릿으로 생성" 버튼을 모두 갖고 있었다. 그 결과 템플릿이 특정 회차에 묶인 것처럼 보였고, 보고 있는 회차가 보관 상태면 템플릿 관리 자체가 막힌 것처럼 동작했다. 템플릿은 회차와 무관하게 항상 쓰는 공용 자산이므로 관리 화면에서 회차/멤버 맥락을 완전히 걷어냈다(`ProjectMemberProvider` 도 걸지 않는다). 대상 회차가 필요한 "항목 생성" 은 회차가 확정된 보드의 템플릿 팝업(결정 34)만 담당한다 — 적용 입구를 한 곳으로 모아 중복도 없앴다.

### 38. 멤버 저장 실패를 추측해서 안내하지 않는다 (Phase J)

`createMember` 가 모든 DB 오류를 "이미 이 회차에 등록된 이메일일 수 있습니다" 로 안내했다. 실제로는 마이그레이션 0007(`users.team_role`) 미적용으로 컬럼이 없어 실패한 경우에도 같은 메시지가 나가, 엉뚱한 곳(중복 이메일)을 찾게 됐다. 이제 unique 위반(`23505`)만 중복으로 명확히 안내하고, 나머지는 DB 가 준 메시지를 그대로 덧붙여 원인이 화면에서 바로 보이게 했다.

### 39. 템플릿 항목의 마감일은 "날짜" 가 아니라 "규칙" 으로 저장 (Phase K)

- **문제**: 템플릿 적용 시 기준 마감일 하나를 받아 모든 항목에 같은 날짜를 넣었다. 실제로는 "사전예약 3일 전에 끝내야 하는 세팅", "출시 하루 전 세팅" 처럼 항목마다 기준이 다르고, 그 기준일은 회차마다 바뀐다. 매 회차 항목별로 날짜를 다시 손대야 했다.
- **결정**: 항목마다 마감일을 정하는 방식을 저장한다(`0016`: `due_phase_name`, `due_offset_days`, `due_date`). 해석 규칙은 `src/lib/templateDueDate.ts` 한 곳에 두고 서버(실제 생성)와 화면(미리보기)이 같은 함수를 쓴다.
  - 일정 기준: 등록한 일정의 **시작일** ± N일. 회차 일정만 갱신하면 마감일이 따라온다.
  - 날짜 직접 선택: 회차와 무관하게 못박을 항목용(기존 방식도 유지해야 한다는 요구).
  - 적용 시 기준일(기본): 종전과 동일하게 적용 화면에서 입력한 기준 마감일. 모든 항목에 규칙이 있으면 이 입력은 쓰이지 않으며, 그 사실을 화면에 표시한다.
- **일정을 id 가 아니라 이름으로 참조**: `saveSchedulePhases` 는 일정을 전체 삭제 후 재삽입하므로 id 가 매번 새로 발급된다. id 로 참조하면 일정을 한 번 수정할 때마다 모든 템플릿 규칙이 끊긴다. 이름은 회차가 바뀌어도 반복되는 개념("출시", "사전예약")이라 참조 키로 더 안정적이다. 대신 이름을 바꾸면 연결이 끊기므로, 그때는 조용히 기준일로 대체하고 "현재 일정에 없음" 을 목록·편집기에 그대로 노출한다.
- **부호 입력을 UI 에서 감춘다**: 저장은 부호 있는 일수 하나지만(`-3`), 입력은 "3일 / 전·후" 로 나눠 받는다. 음수 입력은 오타와 오해가 잦다.

### 40. 담당자 없이 항목 생성 허용 — 알림은 태그 없이 채널로 (Phase K)

- **문제**: `assignee_id` 가 필수라, 담당자가 정해지기 전에는 "이 세팅이 필요하다" 는 사실 자체를 기록할 수 없었다. 실제 일정은 항목 파악이 먼저, 배정이 나중인 경우가 많다.
- **결정**: `tasks.assignee_id` 를 nullable 로 바꾸고(`0016`) 담당자 미지정 상태를 1급 상태로 다룬다.
  - 화면: 생성/수정 모달과 카드 담당자 select 에 "담당자 미지정" 선택지를 둔다. 빈칸은 로딩처럼 보이므로 목록에서는 점선 배지로 "담당자 미지정" 을 명시한다. 보드 필터에 건수와 함께 "담당자 미지정" 을 추가해 배정 대기 목록을 모아 볼 수 있게 했다.
  - 알림: 담당자가 없으면 부를 사람이 없으므로 @멘션 없이 채널에만 보낸다(문구도 "담당자가 아직 없습니다. 확인/담당 지정 부탁드립니다"). 반면 **배정 알림**(`notifyTaskAssigned`)과 **크론 다이제스트**는 특정 담당자에게 보내는 성격이라 미지정 항목은 보내지 않는다(다이제스트는 `user_id` 가 필수라 애초에 예약도 불가).
  - 템플릿 적용도 담당자 미지정을 허용한다. 그래서 멤버가 0명인 회차에서도 템플릿으로 항목을 먼저 만들 수 있다(종전에는 전체 항목 배정이 강제라 막혀 있었다).
- **멤버 삭제 정책은 그대로 둔다**: 담당자가 null 이 될 수 있게 됐지만, 멤버 삭제 시 담당 항목을 자동으로 미지정으로 되돌리지는 않는다(FK 로 계속 막는다). 사람을 지웠다는 이유로 배정 정보가 조용히 사라지는 것이 더 위험하다.

### 1. Vite SPA → Next.js(App Router) 마이그레이션

명세는 Server Actions, 미들웨어, RSC, Vercel Cron, `/tasks/[id]` 딥링크를 전제하지만, 인수받은 산출물은 Vite + React SPA 였다. Vite 에서는 이 요구를 구현할 수 없어 Next.js(App Router)로 마이그레이션했다. 기존 JSX/Tailwind 마크업은 보존하고 라우트 분리와 서버/클라이언트 분리만 수행했다. (사용자 확인을 받은 유일한 지점)

### 2. Next.js 14 + React 18 채택

기존 `peerDependencies` 가 React 18.3.1 이라 호환성을 위해 Next 14(App Router, Server Actions 안정판)를 선택했다. Next 14.2.x 는 보안 패치 버전(14.2.35)으로 고정했다.

### 3. `src/` 디렉터리 + `@/*` alias 유지

기존 코드가 `src/` 기준이므로 `src/app` 구조를 유지했다. 명세의 `lib/db/...`, `types/index.ts`, `lib/notifications/` 는 각각 `src/lib/db/...`, `src/types/index.ts`, `src/lib/notifications/` 로 해석했다. `supabase/` 와 `middleware.ts` 는 루트에 둔다.

### 4. 미사용 의존성/컴포넌트 제거

Figma 템플릿이 포함한 다수의 미사용 라이브러리(MUI, recharts, react-dnd, embla, sonner, 다수 radix 등)와 화면에서 쓰이지 않는 shadcn `ui/` 컴포넌트를 제거했다. 실제 화면은 lucide 아이콘 + 순수 마크업만 사용한다.

## 데이터/타입

### 5. `changed_by` 는 이름으로 매핑

DB `task_history.changed_by` 는 uuid 지만 기존 화면은 사람 이름 문자열을 렌더한다. 마크업 보존을 위해 조회 계층에서 uuid → 이름으로 변환해 `TaskHistory.changedBy` 에 이름을 담는다.

### 6. `Template.itemCount` 는 파생 값

정본 타입에는 없지만 `/templates` 화면이 사용한다. DB 컬럼이 아니라 `template_items` 개수에서 매퍼가 계산한다. (HANDOFF_REPORT 4-1 참조)

### 7. DB 타입은 수동 정의

`any` 금지 원칙에 따라 `src/lib/db/database.types.ts` 를 스키마와 1:1로 수동 작성했다. 로컬 Supabase 연결 후 `pnpm gen:types` 로 자동 생성본으로 교체 가능하다.

## 권한/인증

### 8. 사전 등록 이메일만 로그인

매직 링크는 `signInWithOtp({ shouldCreateUser: false })` 로 발송해 auth.users 에 존재하는(사전 등록된) 이메일만 링크를 받는다. `getCurrentUser` 는 추가로 `public.users` 프로필 존재를 확인한다.

### 9. 항목 수정 버튼은 관리자에게만 노출

명세에 항목 수정 권한 주체가 명시되지 않아, 생성과 동일하게 관리자 전용으로 판단했다. 서버(액션 + RLS)에서 강제하고 UI 버튼도 관리자에게만 노출한다.

### 10. 담당자 tasks 컬럼 제한은 서버 액션이 담당

RLS 는 행 단위라 담당자가 자신의 task 행을 update 하는 것까지만 통제한다. 담당자가 상태 외 필드를 바꾸지 못하도록 하는 컬럼 단위 제한은 서버 액션(담당자는 상태 전환만 허용)이 담당한다.

## 알림

### 11. 웹훅은 단일 채널, 수신자는 메시지 본문으로 구분

웹훅이 단방향·단일 채널이라 사용자별 라우팅이 불가능하므로, 메시지 본문에 담당자 이름을 넣어 구분한다.

### 12. dedupe 는 다이제스트 단위

크론 다이제스트는 담당자당 한 건으로 합쳐 보내므로 dedupe_key 를 `digest:{user_id}:{date}`, 관리자 마감초과 통지는 `overdue_admin:{date}` 로 구성했다(명세의 `due_soon:{task_id}:{date}` 형식을 다이제스트 단위로 일반화). 즉시 발송 알림은 dedupe 대상이 아니라 로그를 남기지 않는다.

### 13. 알림 실패는 액션을 실패시키지 않음

웹훅 전송 실패가 사용자 액션 전체를 막지 않도록 전송을 try/catch 로 감싸 콘솔에 기록한다. 입력 검증 실패는 기존 UI 오류 표시로 사용자에게 명확히 알린다.

## 스토리지

### 14. 스크린샷 표시 위치 추가

기존 화면은 스크린샷을 저장/표시하지 않았다. `Task.screenshotUrl` 이 타입/DB 에 존재하므로, 완료 요청 시 파일 업로드(비공개 버킷) 후 상세 화면에 서명 URL 링크("스크린샷 보기")를 기존 톤으로 추가했다.

## 사용자 요청 반영 (초기 명세 이후)

### 15. 로그인 우회 토글

`NEXT_PUBLIC_AUTH_BYPASS=1` 이면 매직 링크 로그인을 건너뛰고 시드 관리자로 접근한다. 로그인 코드(매직 링크/콜백/미들웨어 세션 갱신)는 그대로 두고, 검사 지점만 우회한다. 우회 시 조회/쓰기는 RLS 를 넘기는 서비스 롤 클라이언트를 사용한다. 로그인 복구는 이 env 를 지우거나 0 으로 두면 된다.

### 16. 웹훅 URL 은 화면 입력값만 사용, 폴백 없음

웹훅 URL 이 자주 바뀌어 사용자(관리자)가 화면에서 입력하도록 했다. `app_settings` 테이블에 저장하고 관리자 보드 상단에서 편집한다. 값이 없으면 알림을 발송하지 않는다(환경 변수/콘솔 폴백 제거).

### 17. 일정(출시 국면)으로 마감일 도출

출시 국면(예: 사전알림, 언팩, 사전예약, 사전개통, 출시)을 `schedule_phases` 에 저장하고 관리자 보드의 "일정" 팝업에서 전체 교체 방식으로 편집한다. 항목 생성/수정 시 국면을 고르면 그 **시작일**이 마감일로 자동 입력된다(직접 수정 가능). 단순함을 위해 항목에 국면 링크는 저장하지 않고 마감일만 저장하므로, 일정 편집이 기존 항목의 마감일을 바꾸지 않는다. 마감 초과/임박/크론 로직은 기존 `dueDate` 를 그대로 사용한다.

## 재설계 (Phase A: 로그인 제거 + 상태 단순화)

### 18. 로그인 완전 제거 + 단일 운영자 프로필

진입 즉시 대시보드를 보여주기 위해 로그인(매직 링크/콜백/미들웨어 보호)을 제거했다. `users` 의 고정 id 행 하나(`PROFILE_USER_ID`)를 "현재 사용자"로 사용하며, 이름/이메일은 좌측 내비의 "프로필 수정"에서 바꾼다. 이 프로필 id 가 항목 이력(`changed_by`)·코멘트(`author_id`) 작성자로 기록된다. 마이그레이션 0005 에서 `users` 의 `auth.users` FK 를 끊고 id 기본값을 부여해 로그인 없이 프로필을 관리한다. 세션이 없으므로 모든 DB 접근은 서비스 롤(RLS 우회)로 이뤄진다 → `SUPABASE_SERVICE_ROLE_KEY` 가 필수다. (역할 기반 권한/`AUTH_BYPASS` 토글은 제거)

### 19. 상태 3개로 축소 (할 일 / 완료 / 반려)

상태가 많아 보기 어렵다는 피드백에 따라 화면 상태를 3개로 줄였다. `in_progress`·`review_requested`(완료요청/승인 플로우)는 제거하고, 기존 데이터는 마이그레이션 0005 에서 '할 일'로 이관한다. enum 값 자체는 과거 이력 표시를 위해 남겨둔다. 라우트는 루트 `/` 를 보드로 통합했다(담당자/관리자 화면 분리 제거).

### 20. 드래그 앤 드롭 칸반 (Phase B)

상세 페이지에 들어가지 않고 보드에서 바로 상태를 바꾸도록 HTML5 드래그 앤 드롭을 붙였다. 노션식으로 어느 컬럼으로든 옮길 수 있게 전이 규칙을 "자기 자신 외 모든 상태로 이동 허용"으로 넓혔고, 반려로 옮길 때만 사유 입력 모달을 띄운다. (초기 명세의 "드래그 칸반 금지"는 사용자 요청으로 뒤집음)

### 23. 담당자 인라인 변경 · 항목별 수동 알림(Teams @멘션) · 카드 상태 버튼 (Phase E)

- **담당자 인라인 변경**: 대시보드 카드에서 담당자 select 로 바로 변경(`changeTaskAssignee`). 상세 진입 불필요.
- **항목별 수동 알림(호출)**: 배치가 아니라 사용자가 카드/상세의 버튼으로 직접 호출(`notifyTaskNow`). 담당자에게 알림을 보낸다.
- **MS Teams @멘션**: 순수 텍스트 웹훅은 태그가 불가능하므로, 멘션 대상이 있으면 Adaptive Card + `msteams.entities` 페이로드로 전송한다(`transport.ts`). 멘션 id 는 담당자의 조직 이메일(UPN)을 사용하므로, users 이메일을 실제 Teams 계정 이메일로 넣어야 태그가 걸린다. 웹훅은 Adaptive Card 를 받을 수 있는 Teams 용(Workflows 또는 Incoming Webhook)이어야 한다. 웹훅 미설정 시 호출 버튼은 안내 메시지를 반환한다.
- **카드 상태 버튼**: 카드에 `allowedNextStatuses` 기반 완료/반려/할 일 버튼을 직접 노출. 상세 진입 없이 밖에서 상태 변경(반려는 사유 모달). 보관된 회차는 읽기 전용.
- **멤버(담당자) 관리**: 로그인이 없어 담당자 목록/이메일을 화면에서 직접 관리해야 한다. 좌측 내비 '멤버 관리'에서 추가/수정/삭제(`createMember`/`updateMember`/`deleteMember`). 이메일은 @멘션 id 로 쓰이므로 실제 조직 이메일을 넣는다. 운영자 프로필은 삭제 불가, 항목/이력에 연결된 멤버는 FK 로 삭제가 막힌다.

### 25. "운영자" 개념 제거 — 모든 멤버는 동등, 현재 사용자는 로컬 선택 (Phase G)

- **문제**: 로그인 제거 이후에도 users 테이블에 `role(admin/assignee)` 과 "고정된 운영자 프로필(PROFILE_USER_ID)" 이 남아 있었다. 그 결과 실제로 누가 상태를 바꾸거나 코멘트를 남겨도 이력에는 항상 같은 고정 계정 이름만 기록됐고, 화면에는 그 프로필만 편집 가능한 "프로필 수정" UI가 별도로 있어 멤버 관리와 개념이 중복됐다.
- **결정**: 관리자라는 지위 자체를 없앤다. 모든 담당자(멤버)는 동등하다.
  - `users.role` 컬럼과 `user_role` enum 을 DB 에서 제거했다(`0008` 마이그레이션). `PROFILE_USER_ID`/`src/lib/profile.ts`/`src/lib/auth.ts`/`ProfileModal`/"프로필 수정" UI 를 모두 삭제했다.
  - 대신 브라우저 로컬(`localStorage`)에 "지금 이 브라우저를 쓰는 사람"을 저장하는 `CurrentUserProvider`를 도입했다. 좌측 내비 하단 select 로 멤버 목록 중 아무나 선택하면 그 사람이 이후 상태변경/코멘트/메모/템플릿 생성의 작성자(`changed_by`/`author_id`)로 기록된다.
  - 이건 진짜 인증이 아니라 자기 신고 방식이다(로그인 없는 사내 도구이므로 의도적 트레이드오프). 서버는 그 id가 실제 존재하는 담당자인지만 검증한다(`requireActor`).
  - 크론 다이제스트의 "관리자 전용 마감초과 요약"도 role 이 없어져 함께 제거했다(담당자별 다이제스트에 이미 본인 마감초과 항목이 포함되므로 중복이었다).
- **직군 라벨**: `users.role`(admin/assignee)은 로그인 제거 이후 권한과 무관해져 그대로 두고, 별도로 `team_role`(사업/기획/TPM/FE/BE, 기본 미정) 컬럼을 추가했다(`0007` 마이그레이션). 멤버 관리 화면에서 추가/수정 시 선택한다.
- **팀즈에서 가져오기**: 웹훅(Incoming/Workflows)은 발송 전용이라 멤버 목록을 읽을 수 없다. 대신 Microsoft Graph(`/teams/{id}/members`, client-credentials)로 조회하는 버튼을 멤버 관리 화면에 추가했다. `MS_GRAPH_*` 환경변수가 없으면 설정 화면 없이 버튼만 있고, 클릭 시 실패 메시지를 그대로 보여준다(요구사항: "활성화 여부를 따지지 말고 실패하면 실패하는 대로"). 조회 성공 시 목록을 보여주고 사용자가 고른 멤버만 `createMembersBulk` 로 일괄 등록한다(이미 등록된 이메일은 자동 제외).

### 22. 템플릿 생성·수정·삭제 (Phase D)

예판마다 반복되는 세팅 묶음을 관리하도록 템플릿 CRUD 를 추가했다. `/templates` 에서 새 템플릿/수정/삭제하며, 편집 모달은 이름·설명과 항목 목록(제목·담당자·환경·차단·컨플루언스/확인 URL·확인 포인트)을 다룬다. 항목은 전체 교체 방식으로 저장한다(수정 시 delete 후 insert). 스키마 변경은 없다(기존 `templates`/`template_items` 사용). 담당자 미지정 항목은 저장을 막아 템플릿 생성 시 담당자 누락 오류를 예방한다.

### 21. 프로젝트(회차) 단위 대시보드 + 보관 + 메모 패널 (Phase C)

예판 회차마다 대시보드를 새로 열고 완료된 회차는 보관하는 요구에 맞춰 `projects` 를 도입했다(0006). `tasks.project_id` 로 회차에 소속시키고, 보드는 `/?project=<id>` 로 한 회차만 보여준다(기본은 최신 활성 회차). "새 대시보드"는 현재 회차를 보관(선택)하고 새 회차를 열어 그리로 이동한다. 보관된 회차는 읽기 전용(생성·드래그·메모 편집 불가)이며 드롭다운으로 언제든 다시 열람한다. 오른쪽 "메모/이슈 로그" 패널(`project_notes`)은 공유가 필요한 맥락(예: 36개월 할부 결제 오류)을 회차 단위로 기록한다. 템플릿 생성은 현재 활성 회차를 대상으로 한다. (초기 명세의 "다중 프로젝트 금지"는 사용자 요청으로 뒤집음)
