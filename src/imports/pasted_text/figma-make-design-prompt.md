# 1단계: Figma Make / v0 디자인 프롬프트

목적은 디자인과 정적 퍼블리싱 페이지를 받는 것이다. 백엔드 로직은 다음 단계에서 Cursor가 붙인다.

---

## 프롬프트 본문

사내 개발팀에서 사용하는 내부 업무 도구의 UI를 만들어줘. 실제 데이터 연동 없이, 목 데이터로 동작하는 정적 화면만 필요해.

### 서비스 설명

BO(백오피스) 세팅 요청을 추적하는 대시보드야. 프론트엔드 개발자가 각 담당자에게 BO 세팅을 요청하고, 담당자가 세팅을 완료하면 개발자가 확인해서 승인하는 흐름이야. 지금은 메신저로 한 명씩 태그해서 독촉하는 걸 이 도구로 대체하려는 거야.

### 디자인 방향

Linear, Attio, Vercel 대시보드 같은 도구의 밀도와 절제된 톤을 기준으로 해줘. 다만 그 서비스들의 브랜드 색이나 분위기를 흉내내라는 게 아니라, 아래 구체적인 원칙을 지켜달라는 의미야.

#### 기본 원칙

- 마케팅 사이트가 아니라 매일 들여다보는 내부 업무 도구야. 화려함보다 정보 밀도와 스캔 가능성이 중요해
- 화면을 훑었을 때 "무엇이 지연됐고 누가 처리해야 하는지"가 3초 안에 보여야 해
- 다크모드는 만들지 마. 라이트모드만
- 데스크톱 우선. 모바일에서 깨지지만 않으면 충분해
- 모든 UI 텍스트는 한국어로 작성해

#### 타이포그래피

- 폰트는 Pretendard를 사용해줘. CDN으로 불러오고, fallback은 `system-ui, sans-serif` 로 지정해
- 본문 14px, 보조 텍스트 13px, 라벨과 배지 12px 을 기본으로 써줘. 16px 이상은 페이지 제목에만
- 폰트 웨이트는 400, 500, 600 세 가지만 써. 700 이상은 쓰지 마
- 한글은 자간을 약간 좁혀줘 (`tracking-tight` 수준)
- 숫자와 날짜, 건수 표시에는 tabular-nums 를 적용해서 자릿수가 흔들리지 않게 해줘

#### 색상

- 기본 팔레트는 무채색 계열(zinc 또는 neutral)로 구성해. 배경은 순백이 아니라 아주 옅은 회색, 카드와 패널은 흰색으로 대비를 만들어줘
- 포인트 컬러를 브랜드처럼 쓰지 마. 색은 오직 상태를 구분하는 데만 사용해
- 인디고, 바이올렛, 퍼플 계열을 쓰지 마. 그라데이션도 쓰지 마
- 상태별 색상은 채도가 낮은 톤으로:
  - 대기: 회색
  - 진행중: 파랑
  - 완료요청: 주황 또는 앰버
  - 완료: 초록
  - 반려: 빨강
- 마감 초과 표시에만 빨강을 강하게 써. 그 외에는 강한 채도를 쓰지 마

#### 형태와 간격

- border-radius 는 6px 를 기본으로 써. 12px 이상 쓰지 마. 완전한 pill 형태는 배지에만 허용
- box-shadow 를 쓰지 마. 요소 구분은 1px 보더와 배경색 차이로만 해. 모달과 드롭다운에만 아주 옅은 그림자를 허용
- 카드 내부 여백은 12px 에서 16px 사이로 유지해. 그 이상 넓히지 마
- 목록 항목 사이 간격은 8px 이하로 촘촘하게
- 콘텐츠 최대 너비를 제한하지 말고 화면 폭을 채워서 써. 좌우 여백은 24px 정도면 충분해

#### 하지 말 것

- 히어로 섹션, 큰 일러스트, 아이콘 위주의 빈 상태 그래픽
- 이모지 사용. UI 어디에도 넣지 마
- 요소를 화면 중앙에 정렬하는 레이아웃. 좌측 정렬을 기본으로 해
- 애니메이션 라이브러리. Tailwind transition 정도만
- 그림자와 보더와 배경색을 동시에 써서 요소를 구분하는 것. 하나만 골라
- 아이콘을 장식으로 쓰는 것. 아이콘은 의미가 있을 때만, 16px 크기로 절제해서

### 기술 제약

- Next.js App Router, TypeScript, Tailwind CSS
- 모든 페이지는 목 데이터로 렌더링해. API 호출, 데이터베이스, 인증 로직은 절대 넣지 마
- 상태 변경, 폼 제출 같은 인터랙션은 로컬 컴포넌트 상태로만 처리해. 새로고침하면 초기화되는 게 정상이야
- 애니메이션 라이브러리를 쓰지 마. 필요하면 Tailwind transition 정도만

### 가장 중요한 요구사항: 타입과 목 데이터 분리

이후 단계에서 실제 백엔드를 연결할 거라서, 아래 구조를 반드시 지켜줘.

`types/index.ts` 에 모든 타입을 정의해줘. 아래 정의를 그대로 사용하고 임의로 바꾸지 마.

    export type TaskStatus = 'todo' | 'in_progress' | 'review_requested' | 'done' | 'rejected'
    export type Environment = 'dev' | 'stg' | 'prd'
    export type UserRole = 'admin' | 'assignee'

    export interface User {
      id: string
      email: string
      name: string
      role: UserRole
    }

    export interface Task {
      id: string
      title: string
      description: string | null
      assigneeId: string
      status: TaskStatus
      environment: Environment
      dueDate: string | null
      isBlocking: boolean
      confluenceUrl: string | null
      verifyUrl: string | null
      verifyPoint: string | null
      screenshotUrl: string | null
      createdAt: string
      updatedAt: string
    }

    export interface TaskHistory {
      id: string
      taskId: string
      fromStatus: TaskStatus | null
      toStatus: TaskStatus
      changedBy: string
      reason: string | null
      createdAt: string
    }

    export interface Comment {
      id: string
      taskId: string
      authorId: string
      body: string
      createdAt: string
    }

    export interface Template {
      id: string
      name: string
      description: string | null
      itemCount: number
    }

`lib/mock-data.ts` 한 파일에만 목 데이터를 넣어줘. 다른 파일에는 하드코딩된 데이터가 하나도 없어야 해. 모든 컴포넌트는 props로 데이터를 받아야 해.

목 데이터는 아래 조건을 만족하게 만들어줘.

- 사용자 6명 (관리자 1명, 담당자 5명)
- 할일 18건 정도. 다섯 가지 상태가 모두 포함되어야 하고, 마감 초과 항목 3건, 마감 임박 항목 2건, 마감일 없는 항목 2건, `isBlocking`이 true인 항목 4건을 포함해줘
- 제목은 실제 통신사 서비스의 BO 세팅처럼 써줘. 예를 들어 "요금제 노출 순서 설정", "가입 가능 연령 제한 값 등록", "프로모션 배너 노출 기간 설정" 같은 식으로
- 코멘트와 이력이 여러 건 달린 항목 최소 2건
- 템플릿 2건

### 만들 화면

#### 로그인

이메일 입력 하나와 전송 버튼. 매직 링크 방식이라 비밀번호 입력란은 없어. 전송 후 "메일을 확인해주세요" 상태 화면도 함께 만들어줘.

#### 담당자 화면 (경로 `/`)

담당자가 로그인하면 보는 기본 화면이야. 자기에게 할당된 미완료 항목만 보여.

- 상단에 미완료 건수와 마감 초과 건수를 간단히 표시
- 마감 초과 항목은 목록 최상단에 시각적으로 구분해서 배치
- 각 항목 카드에 제목, 환경 배지, 마감일(D-day 형태), 차단 항목 표시, 현재 상태
- 카드에서 바로 "진행중으로 변경", "완료 요청" 버튼을 누를 수 있게
- 반려된 항목은 반려 사유가 카드에 바로 보이게 강조
- 할 일이 없을 때의 빈 상태 화면도 만들어줘

#### 관리자 보드 (경로 `/board`)

- 상태별 5개 컬럼의 칸반 보드. 드래그 앤 드롭은 만들지 마
- 상단에 전체 진척률 바, 전체 건수, 미완료 차단 항목 건수
- 필터 영역: 환경 선택, 담당자 선택, 차단 항목만 보기 토글
- 각 카드에 제목, 담당자 이름, 환경 배지, 마감일, 차단 항목 표시
- "완료요청" 컬럼의 카드에는 확인이 필요하다는 게 눈에 띄게
- 우측 상단에 항목 생성 버튼, 템플릿 불러오기 버튼

#### 항목 상세 (경로 `/tasks/[id]`)

가장 중요한 화면이야. 알림 링크를 타고 들어오는 목적지라서 여기서 모든 처리가 끝나야 해.

- 제목, 설명, 담당자, 환경, 마감일, 차단 여부
- 컨플루언스 링크와 확인 URL은 새 탭으로 열리는 버튼 형태로. 확인 URL 버튼 바로 아래에 `verifyPoint` 텍스트를 붙여서 무엇을 확인하면 되는지 알 수 있게 해줘
- 상태 변경 액션 영역. 현재 상태에 따라 가능한 버튼만 노출돼야 해
  - todo 상태면 "진행중으로 변경"
  - in_progress 상태면 "완료 요청" (스크린샷 첨부 영역 포함, 선택 사항)
  - review_requested 상태면 관리자용 "승인"과 "반려" 버튼. 반려를 누르면 사유 입력란이 나오고, 사유 없이는 제출할 수 없어
  - done 상태면 액션 없음
- 코멘트 목록과 입력창
- 상태 변경 이력 타임라인. 누가 언제 어떤 상태로 바꿨는지, 반려면 사유까지
- 관리자와 담당자에게 보이는 버튼이 다르니까, 화면 어딘가에 역할을 전환해볼 수 있는 토글을 임시로 넣어줘. 나중에 제거할 개발용 장치라는 주석을 달아줘

#### 항목 생성 및 수정 모달

- 제목, 설명, 담당자 선택, 환경 선택, 마감일, 차단 여부 체크박스, 컨플루언스 URL, 확인 URL, 확인 포인트
- 제목과 담당자, 환경은 필수. 유효성 오류 표시도 만들어줘

#### 템플릿 (경로 `/templates`)

- 템플릿 목록. 각 템플릿의 이름, 설명, 포함된 항목 수
- 템플릿 상세에서 포함 항목 목록 확인
- "이 템플릿으로 생성" 버튼. 누르면 환경과 기준 마감일만 입력받는 모달

### 공통 컴포넌트

아래는 재사용 컴포넌트로 분리해줘.

- 상태 배지 (5가지 상태별 색상 구분)
- 환경 배지 (DEV, STG, PRD 구분)
- 차단 항목 표시
- 마감일 표시 (D-day 계산, 초과 시 강조, 마감일 없으면 빈 상태)
- 담당자 표시 (이름 및 이니셜)
- 할일 카드

### 반드시 지킬 것

- `lib/mock-data.ts` 외의 어떤 파일에도 하드코딩된 데이터를 넣지 마
- `types/index.ts` 의 타입 정의를 그대로 유지해
- API 라우트, 데이터베이스, 인증, 폼 서버 처리 로직을 만들지 마
- 통계 차트, 실시간 기능, 드래그 앤 드롭, 다국어 처리는 만들지 마

## 결과물 확인 체크리스트

Figma Make나 v0의 결과를 받은 뒤 다음을 확인하고 2단계로 넘어간다.

- `types/index.ts` 의 타입 정의가 지시대로 유지되었는지
- `lib/mock-data.ts` 외에 데이터가 흩어져 있지 않은지
- 다섯 가지 상태, 빈 상태, 마감 초과, 반려 사유 노출이 모두 화면에 구현되었는지
- 상세 화면의 확인 URL 버튼과 확인 포인트 텍스트가 함께 있는지
- 역할 전환 토글이 상세 화면에 있는지
